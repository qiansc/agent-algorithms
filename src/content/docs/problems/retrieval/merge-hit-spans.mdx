## 题目

把检索命中的原文区间里，**同一文档**内重叠或首尾相接的合并成一段。

- 每个命中写成 `(文档 ID, 起始 token, 结束 token)`，左闭右开：`(1, 2, 6)` 表示文档 1 的第 2、3、4、5 个 token。
- 首尾相接指前一段的终点等于后一段的起点，例如 `[5, 8)` 和 `[8, 10)`。
- 不同文档互不影响。输出按文档 ID 升序，同一文档内按起点升序。
- 输入顺序任意，可能有完全相同的命中；输入为空时返回空列表。
- 起点不小于终点时抛出错误。

## 样例

输入：`[(2, 1, 5), (1, 8, 10), (1, 2, 6), (1, 5, 8), (1, 13, 14)]`

输出：`[(1, 2, 10), (1, 13, 14), (2, 1, 5)]`

这个样例能抓三种错误：

- `(1, 5, 8)` 和 `(1, 8, 10)` 首尾相接。条件写成 `start < 上一段终点` 会把它们拆开，得到 `(1, 2, 8)` 和 `(1, 8, 10)` 两段。
- `(2, 1, 5)` 的起点 1 比文档 1 最后一段的终点 14 小。不检查文档 ID，它会被并进文档 1。
- 输入是乱序的，不排序直接扫描会漏掉合并。

另一个常错的输入是 `[(1, 2, 10), (1, 4, 6)]`，答案是 `[(1, 2, 10)]`。合并时直接用新区间的终点，会得到 `(1, 2, 6)`，丢掉 `[6, 10)`。

## 思路

按（文档, 起点）排序后扫一遍，每个区间只和结果表的最后一段比：能接上就合并，终点取较大值；接不上就另起一段。

区间按起点排好后，新区间如果要合并，对象一定是结果表的**最后一段**。结果表里各段之间都有空隙，越往后起点越大。新区间的起点不比之前任何区间小，它要么接在最后一段上，要么在它之后另起一段，够不到更早的段。

所以每读一段只判断一次：同一文档，并且 `start <= 最后一段的终点`，就合并；否则追加一段。

排序也让同一篇文档的区间挨在一起。判断时再加上“文档相同”，就不会跨文档合并。

终点要取较大值，因为排序只保证起点有序。`[(1, 2, 10), (1, 4, 6)]` 里，后读到的 `[4, 6)` 整个落在 `[2, 10)` 里面。直接用 6 覆盖终点，`[6, 10)` 这 4 个 token 就丢了。

合并后，样例送进上下文的 token 从 14 个降到 13 个。5 个命中的长度依次是 4、2、4、3、1，合并后三段是 8、1、4，token 5 原来被命中两次，现在只留一份。

## 代码

<Solution slug="merge-hit-spans" />

Python 的元组可以直接比大小，`sorted(hits)` 就是按（文档, 起点, 终点）排序。JavaScript 的 `sort` 不传比较函数时会把元素转成字符串再比，`[10, 1, 2]` 会排在 `[9, 1, 2]` 前面，所以 TypeScript 版写了三层比较。

TypeScript 版先用 `[...hits]` 复制再排序，合并时直接改结果表最后一段的终点 `last[2]`。结果表里的数组都是新建的，不会改到输入。

## 复杂度

n 是命中区间的个数。

- **时间 O(n log n)**：排序占 O(n log n)，之后的扫描每个区间只做一次比较，O(n)。
- **空间 O(n)**：排序后的副本和结果表各最多 n 项。如果命中本来就按（文档, 起点）排好，可以边读边合并，手上只留最后一段，额外空间降到 O(1)。

## 自测：两个容易写错的输入

<Aside type="caution" title="先在纸上算，再跑代码">
`[(1, 0, 3), (1, 3, 5)]` 的正确答案是 `[(1, 0, 5)]`。如果你得到两段，多半把条件写成了 `start < 终点`，首尾相接没有并上。

`[(2, 0, 4), (1, 0, 4), (2, 3, 6)]` 的正确答案是 `[(1, 0, 4), (2, 0, 6)]`。如果你得到 `[(1, 0, 6)]`，说明合并时没有比较文档 ID。
</Aside>

本页代码还对空输入、只有一段、被大区间整个包住、相隔一个 token、完全重复的命中、起点不小于终点（应报错）和 40 段随机区间跑过测试。随机测试会逐个 token 检查：合并前后覆盖的 token 完全相同，相邻两段之间真的有空隙。

## 延伸：相隔几个 token 的两段也要拼起来呢？

两段命中只隔两三个 token 时，送给模型的原文被拆成两截，读起来不连贯。新规则：同一文档里两段之间空着不超过 `gap` 个 token，也拼成一段，空隙一起带上。

只改判断条件：`start <= 最后一段的终点 + gap`。`gap = 0` 时就是原题。

<Solution slug="merge-hit-spans" file="followup" />

拿样例试。`[2, 10)` 和 `[13, 14)` 之间空着 10、11、12 三个 token：

- `gap = 2`：3 > 2，不拼，结果和原题一样，`[(1, 2, 10), (1, 13, 14), (2, 1, 5)]`。
- `gap = 3`：13 ≤ 10 + 3，拼成 `[(1, 2, 14), (2, 1, 5)]`，总长 16 个 token，比原题的 13 个多出 3 个，正好是被补进来的空隙。

有了 `gap`，合并会多读进一些没被命中的 token。上下文预算紧时，要把这部分算进去。
