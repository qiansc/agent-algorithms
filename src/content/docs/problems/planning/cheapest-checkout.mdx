  const width = withBucket ? 11 : 10;

  const paid = [];

  for (let j = 0; j < width; j++) {
    const cell = cells[j];
    if (!cell) {
      plan.push('');
      paid.push('');
      tones[`0,${j}`] = 'ghost';
      tones[`1,${j}`] = 'ghost';
      continue;
    }
    plan.push(planText(cell[1]));
    paid.push(paidOf(cell[0]));
  }
  for (const [key, tone] of Object.entries(marks)) tones[key] = tone;
  return { plan, paid, tones, width };
};

## 题目

点外卖时挑一些加购品凑满减，求最少实付和要加哪几件。

- 输入：必点菜小计 `required` 元；加购品价格 `prices[i]`，每件最多加一次；满减档 `tiers`，`[t, d]` 表示总额达到 t 元减 d 元。
- **只能用一档**：在够到的档里取减得最多的。实付 = 购物车总额 − 减额。
- 返回 `[最少实付, 要加的加购品下标]`，下标升序。

- 实付相同时，加的件数少的优先；件数也相同，取下标列表字典序最小的。
- 什么都不加也是一种方案。没有满减档时，就是原价。
- `required` 是非负整数，价格是正整数，每档满减要求 `0 < d ≤ t`。不满足时抛出异常。
- 规模：加购品最多 100 件，门槛最多 1000 元。

## 样例

三个样例的满减都是 `tiers = [[30, 8], [50, 20]]`，即满 30 减 8、满 50 减 20。样例 1 和 3 的加购品依次是米饭 3 元、卤蛋 4 元、拍黄瓜 6 元、鸡腿 11 元。

| required | prices | 输出 | 说明 |
|---|---|---|---|
| 40 | `[3, 4, 6, 11]` | `[30, [1, 2]]` | 加卤蛋和拍黄瓜，正好 50，减 20 |
| 24 | `[2, 4, 6]` | `[22, [2]]` | 加 6 或加 2 + 4 都到 30、实付 22，选件数少的 |
| 55 | `[3, 4, 6, 11]` | `[35, []]` | 已经过了最高档，再加只会多付 |

第一个样例卡两种凭直觉的凑法。“找一件能凑到 50 的最便宜的”会选鸡腿，总额 51，实付 31。“从最便宜的开始加，直到够 50”会加 3、4、6，总额 53，实付 33。两种都比 30 多。冲高一档也可能更省：不加菜付 32，凑到 50 付 30。

## 思路

用子集和 DP 求出能凑出的所有总额，表只开到最高门槛，再逐个总额算实付取最小。

实付只取决于购物车总额 T。样例 1 里，T 从 40 到 49 只够 30 档，实付 T − 8；到 50 减 20，实付掉到 30；再往上每多 1 元就多付 1 元。

  <Bars items={curve} min={0} max={45} digits={0} />
</Figure>

加购品只通过总价影响实付。问题拆成两步：

1. 哪些总额凑得出来？这是子集和问题：哪些和能由若干个数（每个最多用一次）加出来。做法同 0/1 背包：一张“总额 → 凑法”的表，逐件加入加购品，从大往小扫，每件只用一次。
2. 对每个凑得出的总额算实付，取最小。

表开多大？50 以上减额固定是 20，总额越大实付越多。所以 50 以上合成一格“≥50”，只留**实际总额最小**的凑法。表宽是“最高门槛 − 必点小计 + 1”，样例 1 是 40 到 49 共 10 格，再加“≥50”。

“≥50”里总额最小的凑法一定找得到吗？拿掉其中任何一件，总额都会掉到 50 以下；不然拿掉后还够 50 又更便宜，和“最小”矛盾。所以它一定是某个 50 以下的格子加一件得来的，而这些格子表里都有。

同一个总额可能有几种凑法。格子里留件数最少的，件数相同留下标字典序最小的。“≥50”这格先比实际总额，再比这两项。

## 代码

格子 j 对应总额 `required + j`，最后一格 `cap = top − required` 就是“≥ 最高门槛”。必点小计已经够到最高门槛时，表的宽度是 0，直接返回不加菜的结果。

比较两种凑法时，Python 直接比较元组 `(总额, 件数, 下标列表)`，列表之间会按字典序逐个比较。TypeScript 没有元组比较，`solution.ts` 里写了 `better` 和 `lexLess` 两个函数，按同样的顺序一项一项比。`Math.max(0, ...arr)` 的 0 对应 Python `max(..., default=0)`，没有满减档时减额是 0。

## 复杂度

n 是加购品件数，W 是表的宽度，等于最高门槛减去必点小计再加 1（不超过 1001）。

- **时间 O(n·W·n)**：每件加购品把表扫一遍，共 n·W 次更新；每次更新要复制和比较一个最长 n 项的下标列表，所以再乘一个 n。如果只要最少实付、不要方案，前面的格子只存“凑不凑得出”，最后一格只存最小总额，就是 O(n·W)。
- **空间 O(W·n)**：每格存一个下标列表。只求金额时是 O(W)。

样例 1 如果得到 32，说明表只开到了 49，越过 50 的总额都丢了。

## 延伸：再叠一张平台券呢？

假设平台另给一张券：店铺满减后还要付 40 元或以上，再减 5 元。实付仍只取决于总额，子集和的表不用改，变的是实付函数和表宽。

“超过最高门槛只会更贵”不再成立。样例 1 里总额到 50 后，店铺减完是 T − 20；T = 60 时减完才到 40，平台券才能用。实付在 60 处又掉一次，最后一次下跌从 50 挪到了 60。一般地，表要开到

`max(最高门槛, 平台券门槛 + 店铺最大减额)`

60 以上才可以合成一格。原题里“必点小计已经过了最高门槛就什么都不加”的提前返回，也要改成和这个新位置比较。

用样例 1 的加购品和满减试两个必点小计：

- `required = 40`：凑到 60 要加 3+6+11，实付 60 − 20 − 5 = 35，不如原来的 30，答案仍是 `[30, [1, 2]]`。
- `required = 57`：原题什么都不加，实付 37。叠了平台券后，加一份米饭凑到 60，实付 35，答案是 `[35, [0]]`。原题的写法在这里会直接返回 37。
