## 题目

写 `group_advantages(groups)`，把每组奖励在组内标准化。对组内每个分数 r，返回

`(r − 本组均值) / 本组标准差`

- `groups` 的每个内层列表是同一个请求多次采样的得分。
- 标准差用**总体标准差**：偏差平方的平均除以组大小 G，不是 G − 1。
- 组内分数全部相同（包括只有一个分数）时，这一组返回全 0。
- 空组返回空列表；`groups` 为空时返回空列表。
- 奖励是绝对值不超过 1000 的整数。返回结构和输入相同，每个数是浮点数，允许 1e-9 的误差。

## 样例

| 输入 | 输出 |
|---|---|
| `[[0, 0, 2, 2], [5, 5], [], [1]]` | `[[-1, -1, 1, 1], [0, 0], [], [0]]` |
| `[[1, 2, 3]]` | `[[-1.2247, 0, 1.2247]]` |
| `[[0, 0, 0, 1]]` | `[[-0.5774, -0.5774, -0.5774, 1.7321]]` |

样例 1 检查两个错误：

- 标准差除以 G − 1，第一组会算成 ±0.866。
- 所有组的分数混在一起算，第二组的两个 5 会拿到 1.459。它们在自己组里一样好，应该是 0。

## 思路

每组单独算：减去本组均值，再除以本组总体标准差。标准差为 0 的组直接给全 0。

### 优势要和谁比

优势是“这次回答比平常好多少”。PPO 用价值网络估计“平常”（见 <ProblemLink slug="gae" />）。GRPO 不用这个网络：同一个请求采样 G 次，用 G 次的平均分当“平常”。

样例 1 第一组 `[0, 0, 2, 2]`，均值是 1。偏差是 −1、−1、1、1。

### 为什么还要除以标准差

不同请求的分数尺度可能差很多，有的题满分 1，有的满分 10。除以组内标准差后，每组优势落在相近的范围，难题和简单题对梯度的影响不会差太多。

第一组的四个偏差平方都是 1，平均是 1，总体标准差是 1，所以优势就是 `[-1, -1, 1, 1]`。

样例 2 `[1, 2, 3]`：均值 2，偏差 −1、0、1，平方的平均是 2/3，标准差 √(2/3) = 0.8165。优势是 −1 / 0.8165 = −1.2247、0、1.2247。

样例 3 `[0, 0, 0, 1]`，四次里只成功一次。均值 0.25，偏差是 −0.25 和 0.75，方差 (3 × 0.0625 + 0.5625) / 4 = 0.1875，标准差 0.4330。成功的那次拿到 0.75 / 0.4330 = 1.7321，三次失败各 −0.5774。少见的成功拿到更大的正优势。

−0.5774 × 3 + 1.7321 = 0。组内优势之和总是 0。

### 两种特殊的组

`[5, 5]`：偏差全是 0，标准差也是 0，直接相除是 0 / 0。两次一样好，看不出该学谁，返回 `[0, 0]`。只有一个分数的 `[1]` 同理，返回 `[0]`。空组返回空列表。

### 为什么不能把所有组混在一起

把样例 1 的七个分数 `[0, 0, 2, 2, 5, 5, 1]` 放在一起算：均值 15 / 7 = 2.1429，总体标准差 1.9588。第二组的 5 得到 (5 − 2.1429) / 1.9588 = 1.459 的正优势。

第二组的请求可能只是更简单，5 分容易拿。混在一起算，模型学到的是“去答简单题”，而不是“同一道题答得更好”。所以比较对象必须是同一个请求的其他尝试。

### 一个检查答案的办法

把第一组改成 `[10, 10, 14, 14]`，答案仍是 `[-1, -1, 1, 1]`。它等于原来每个分数乘 2 再加 10。加的 10 被均值减掉，乘的 2 在偏差和标准差里约掉。代码在这个输入上给出别的数，多半是均值或标准差算错了。

两个版本逐行对应。奖励是绝对值不超过 1000 的整数，一组的和远小于 `Number.MAX_SAFE_INTEGER`，两种语言里求和都是精确的；组内分数全相同时，均值恰好等于这个整数，偏差恰好是 0，所以用 `std == 0` 判断不会受浮点误差影响。Python 返回 `0.0`、`-1.0` 这样的浮点数，TypeScript 里数字不分整数和浮点数，两者按数值比较相等。

## 复杂度

B 是组的个数，N 是所有组里奖励的总数。

- **时间 O(B + N)**：每组扫三遍（求和、算偏差、算平方和），每个奖励被处理常数次；空组也要花常数时间放一个空列表。
- **空间**：输出占 O(B + N)。计算时每组临时存一份偏差，额外空间是 O(最大组的大小)。

## 自测：两个容易写错的输入

<Aside type="caution" title="先在纸上算，再跑代码">
`[[0, 0, 2, 2]]` 的正确答案是 `[[-1, -1, 1, 1]]`。如果你得到 ±0.866，是用了样本标准差（除以 G − 1），例如 Python 的 `statistics.stdev`；总体标准差对应的是 `statistics.pstdev`。

`[[5, 5], [1]]` 的正确答案是 `[[0, 0], [0]]`。如果程序抛了 `ZeroDivisionError`，或者 TypeScript 里得到 `NaN`，是漏了标准差为 0 的判断。
</Aside>

本页代码还测过：`groups` 为空、负奖励 `[-3, -1]`（得 `[-1, 1]`）、平移加缩放后的 `[10, 10, 14, 14]`，以及随机生成的 7 组（含空组和全相同的组）与 `statistics.pstdev` 写法对拍。

## 延伸：分母写成 std + ε，答案还一样吗？

很多实现不判断 `std == 0`，而是统一除以 `std + ε` 防止除零，ε 是很小的正数。现在奖励可以是任意实数，用这种写法重算。

均值和偏差不变，只改最后的分母。全相同的组不用单独处理：偏差全是 0，0 除以 ε 还是 0。

代价是“乘一个正数答案不变”不再严格成立。标准差越小，ε 占的比重越大：

- `[10, 10, 14, 14]`、ε = 0.01：标准差 2，优势是 ±2 / 2.01 = ±0.9950，和 ±1 差别很小。
- `[0, 0, 0.02, 0.02]`、ε = 0.01：这组和上一组只差一个缩放，标准差是 0.01，优势变成 ±0.01 / 0.02 = ±0.5，只剩一半。

奖励尺度很小时，ε 要跟着调小，否则优势会被系统性地压低。
