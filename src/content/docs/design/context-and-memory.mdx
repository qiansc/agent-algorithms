一位用户在一次对话里说了 30 多句话。先说“和上周五那单一样”，中途说“我乳糖不耐，别给我含奶的”，又说“这三天出差，送到酒店”，最后改口“算了，咖啡不要了”。一周后他再打开助手，说“老样子”。

助手要分得清：哪些话只对那一单有效，哪些要一直记着，哪些过几天就该忘。这一页讲会话状态和长期偏好怎么存、怎么取、怎么删。

## 题目

设计点餐助手的记忆层。

- 会话内：购物车、本单地址、送达时间等约束，在 30 轮对话后仍然准确，用户改口时以最新的为准。
- 跨会话：忌口、常用地址、口味习惯，下次能用上；用户能看到助手记了什么，能删。
- 提示词长度有限，不能每轮都塞进全部历史和全部偏好。
- 健康相关的信息要格外谨慎。

方案要回答：会话状态和聊天记录是什么关系；长期偏好记什么、不记什么、记多久；什么时候取哪些偏好；用户怎样查看和删除。

## 先想清楚的几件事

### 聊天记录能不能直接当状态用？

不能。用户第 5 轮说“送公司”，第 18 轮说“送酒店”，第 27 轮说“地址还是用公司的吧”。靠模型在 30 轮记录里找“最新的地址”，每一轮都可能找错，找错了也没有代码能发现。

会变的东西要有一份结构化的当前值，只此一份。模型要改它，得调工具，改完能校验。聊天记录只用来理解语气和指代，不当作事实来源。

### 购物车放在哪？

放在购物车服务里。会话状态只存 `cart_id` 和一份只读快照。购物车的内容由加购、删除接口维护，不靠模型“记得”。模型记错了，用户就会在确认卡上看到一份陌生的订单。

### 信息分几种寿命？

| 寿命 | 例子 | 存在哪 |
|---|---|---|
| 这一单 | “半小时内送到”“这单不要香菜”“今天请同事喝，要 5 杯” | 会话状态，订单完成就清掉 |
| 有期限 | “这三天出差，送到酒店” | 长期偏好，带有效期 |
| 长期 | “我乳糖不耐”“我不吃辣” | 长期偏好，用户明说，不过期 |
| 推断 | 最近 3 单咖啡都选少冰 | 长期偏好，攒够证据才生效，会过期 |

把“这一单”的话写进长期偏好是最常见的错。“今天要 5 杯”记成长期偏好，以后每次都给他点 5 杯。

### 明说和推断谁优先？

明说的优先。用户说“正常冰”，哪怕过去 10 单都是少冰，也按正常冰。

推断只用来填用户没说的空，而且只用在确认卡上一眼能看出、一下能改掉的地方，比如冰度、杯型。忌口、过敏这类健康信息只接受明说，不做推断：连续三次没点含奶的饮料，不代表他乳糖不耐。

会话状态是一个 JSON 对象，每轮都完整放进上下文。它只有几百个 token，比 30 轮对话原文便宜得多，也准确得多：

```json
{
  "session_id": "s_0c41",
  "stage": "confirming",
  "base_order": { "order_id": "o_1113_a", "store": "绿碗轻食" },
  "cart": {
    "cart_id": "c_7f3a",
    "snapshot": ["鸡胸肉藜麦沙拉 ×1", "南瓜浓汤 ×1",
                 "冰美式 中杯 少冰 ×1"]
  },
  "address": {
    "id": "addr_office", "label": "公司",
    "source": "user_said_turn_27"
  },
  "constraints": { "deliver_within_min": 30, "no_ingredients": [] },
  "fallbacks": [],
  "pending_orders": []
}
```

几个字段的用意：

- `address.source` 记着这个值来自第 27 轮，用户问“为什么送公司”时能答上来。
- `constraints` 只放这一单的条件。
- `fallbacks` 记录降级经过。这一单还没发生降级，格式见<DesignLink slug="out-of-stock-fallback" />。
- `pending_orders` 放结果未知的订单，生成新确认卡前要先看它，见<DesignLink slug="confirm-before-payment" />。

## 关键细节

### 按阶段取偏好

每个阶段只取用得上的偏好。放多了，模型会在不相关的地方用上它们：用户在问“这家店几点关门”，模型却开始解释“已为你避开含奶饮品”。

| 阶段 | 取哪些 | 用来做什么 |
|---|---|---|
| 搜索、选菜 | 忌口、口味（辣度、冰度） | 过滤和排序候选 |
| 组购物车 | 规格习惯（杯型、冰度） | 填用户没说的规格，并在确认卡上显示 |
| 确认、下单 | 地址、联系方式 | 预填，确认卡上必须显示 |
| 查配送、售后 | 不取偏好 | 只看订单 |

忌口是例外：搜索阶段用它过滤，确认阶段还要用它再查一遍购物车，因为购物车里可能有用户手动加的东西。

### 写入长期偏好前先问

用户说“我乳糖不耐”，助手当场照做，这一单避开含奶的。然后问一句：“要我记住吗？以后都自动避开含奶的。”用户说好，才调 `tell`。不问就记，用户总有一天会发现，助手“知道”一些他没想让它记的事。

推断的偏好不用问，但用到时要说明来源，例如确认卡上写“少冰（按你最近的习惯）”。

### 什么不记

- 支付信息：卡号、密码、验证码，一律不进模型能看到的任何存储。
- 别人的信息：“送给我妈，电话 139……”，这是这一单的收货人，不是用户本人的偏好，订单完成后从会话状态清掉。
- 一次性的情绪和场景：“今天心情不好想吃甜的”“今天请客”。
- 从行为推断的健康信息：前面说过，忌口只接受明说。

### 用户能看、能删

`visible` 的输出直接渲染成“我的偏好”页面。每条显示值、来源（“你说的”或“根据最近 3 单”）和写入时间，旁边一个删除按钮。用户在对话里说“别记我在酒店的事了”，也走同一个 `forget`。

删除是真删：明说的记录、推断结果和观察历史一起删掉。测试“忘掉之后要重新攒证据”验证的就是这点：删除地址后，第 4 天再观察到一次“公司”，`get` 仍返回 `null`。

### 旧对话怎么处理

最近 8 轮保留原文，更早的不做自由摘要。有用的信息在发生时已经写进会话状态（约束、地址、降级记录），旧对话里剩下的只是寒暄和中间过程。自由摘要还可能把“用户考虑过冰拿铁但没要”压成“用户想要冰拿铁”。

## 常见的坑

<Aside type="caution" title="记忆层最容易出的错">
**让模型记购物车。** 购物车以服务端为准，会话状态里只存 id 和快照。模型说“已加入购物车”而接口没调，用户下单时才发现少了东西。

**把一次性的话写成长期偏好。** “这单送公司”变成“常用地址：公司”，周末在家点餐也送去公司了。

**删除只删一半。** 只删推断结果，不删观察历史，再点一单就又推断回来，用户会觉得“删除”是假的。

**偏好全量塞进提示词。** 20 条偏好每轮都带上，模型会在无关的回答里提起它们，也更容易把它们和当前约束搞混。

**推断健康信息。** 用户连续几次没点含奶的，就记成“乳糖不耐”，再在别的地方展示出来。这是用户没说过的隐私推断。
</Aside>

## 延伸：明说的偏好和后来的行为对不上怎么办？

用户第 1 天说过“冰度要正常冰”，之后第 2、3、4 天连续三单都手动改成了少冰。按代码，第 4 天的 `observe` 返回 `true`（推断偏好已经是少冰），可第 5 天 `get` 仍返回“正常冰”，因为明说的优先。测试里“延伸：行为和明说的冲突”就是这组数据。

`observe` 返回 `true` 而 `get` 返回别的值，就是冲突的信号。这时不要自己改掉明说的偏好，用户可能只是这几天天热。在下一次用到冰度时问一句：“你之前说要正常冰，最近三次都选了少冰，以后默认少冰吗？”用户说是，就用 `tell` 覆盖；说不是，就保持原样，并且这条推断在 60 天内不再提醒，免得反复打扰。

忌口不走这个流程。用户说过乳糖不耐，后来自己点了一杯拿铁，可能是给别人点的。忌口只由用户明确修改，行为再多也不触发提醒。
